# Фронтенд «Цифровой механик»

Веб-клиент механика: выбор машины и проверки, заключение помощника по результату диагностики, диалог с помощником и заявка на дефектовку в ТОиР.

## Быстрый запуск

Нужны Node.js версии 20.19 и выше или 22.12 и выше и Python 3.10 или новее для mock-сервисов.

### 1. Mock-сервисы

Папка `neurodvs_mock` с заглушками ML и ТОиР выдаётся организаторами и в репозитории не хранится. В ней:

```bash
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
```

На Linux и macOS вместо второй команды — `source .venv/bin/activate`.

Сервисы запускаются в двух терминалах, в каждом окружение активируется заново:

```bash
uvicorn mock_ml.app:app --port 8001
```

```bash
uvicorn mock_toir.app:app --port 8002
```

Сервис работает, если страница `http://127.0.0.1:8001/health` (для ТОиР — порт `8002`) открывается без ошибки.

### 2. Приложение

В папке `frontend`:

```bash
cp .env.example .env
npm install
npm run dev
```

В командной строке Windows вместо `cp` используйте `copy`.

Приложение откроется по адресу `http://localhost:5173`. Адрес `http://127.0.0.1:5173` не сработает: сервер разработки слушает только `localhost`.

### 3. Адреса сервисов

Адреса задаются в `frontend/.env`. После правки файла перезапустите `npm run dev`.

| Переменная | Сервис | Значение в `.env.example` |
|---|---|---|
| `VITE_MOCK_ML_URL` | ML-сервис, `POST /diagnose` | `http://127.0.0.1:8001` |
| `VITE_MOCK_TOIR_URL` | ТОиР, `POST /tickets` | `http://127.0.0.1:8002` |
| `VITE_AGENT_URL` | ИИ-агент, полный адрес вебхука | пусто — адрес выдаёт команда агента |

Что работает без чего:

| Чего нет | Что не работает | Что работает |
|---|---|---|
| Mock ML | Результат диагностики и заявка | Список машин и проверок, вопросы помощнику |
| Mock ТОиР | Отправка заявки | Диагностика, диалог, форма и предпросмотр заявки |
| Адреса агента или доступа к нему | Результат диагностики, ответы помощника, заявка | Список машин и проверок |

Результат диагностики механику сообщает помощник, поэтому без агента приложение его не покажет.

Если переменная не задана, вверху страницы появляется предупреждение с её именем.

### Проверки перед коммитом

```bash
npm run typecheck
npm run build
```

## Демонстрационные сценарии

Проверки для сценариев подобраны в данных mock-сервисов. Другие подходящие проверки — в разделе «Проверки для демонстрации».

### С1. Отклонение, заявка с подтверждением

1. Найдите машину `M333YK47` и выберите проверку `S-0005`.
2. Нажмите «Получить результат диагностики».
3. Дождитесь заключения помощника: это может занять несколько минут. В заключении — что обнаружено, что проверить и ссылки на страницы руководства.
4. Нажмите «Оформить заявку на дефектовку» под заключением. Форма заполнится по черновику помощника: заключение, работы, запчасти, источники. Сверьте их с руководством и поправьте, если нужно.
5. Нажмите «К предпросмотру» и проверьте состав заявки. До этого шага включительно в ТОиР ничего не отправляется.
6. Нажмите «Подтвердить и отправить в ТОиР». В ленте появится номер заявки, в панели «История заявок» — запись о ней.
7. Обновите страницу: запись в истории останется.

Сценарию нужны все три сервиса: агент, ML и ТОиР. Если помощник не приложил черновик заявки, форма заполняется расчётом приложения, а в разделе «Источники» механик сам выбирает руководство и вводит номер страницы из него.

### С2. Уточняющий вопрос помощнику

1. Выберите машину и проверку, например `M333YK47` и `S-0005`.
2. Введите вопрос в поле «Сообщение помощнику» или продиктуйте его, нажав кнопку с микрофоном.
3. Нажмите «Отправить». Ответ помощника появится в ленте.

Нужен адрес агента в `VITE_AGENT_URL` и доступ к нему из сети, где открыто приложение. Если агент недоступен, в ленте появится сообщение с причиной.

### С3. Анализ не выполнен

1. Найдите машину `P456AT178` и выберите проверку `S-0003`.
2. Нажмите «Получить результат диагностики».
3. В ленте появится заключение помощника: запись разобрать не удалось, её нужно повторить. Кнопки заявки нет.

Текст заключения пишет агент. Кнопку заявки приложение не показывает само, по ответу ML-сервиса, что бы ни написал агент.

## Состояния интерфейса

| Состояние | Что видит механик |
|---|---|
| Машина или проверка не выбраны | Кнопка диагностики недоступна, под ней подсказка, что выбрать |
| Идёт запрос диагностики | Кнопка диагностики занята, в ленте пометка «Запрашиваем результат диагностики…» |
| Помощник готовит заключение по результату диагностики | Кнопка диагностики занята, в ленте пометка «Помощник готовит заключение по результату диагностики…», новый вопрос не отправляется |
| Заключение не получено | Сообщение с причиной и кнопка «Запросить заключение ещё раз». Заявка не предлагается |
| Помощник готовит ответ на вопрос | В ленте пометка «Помощник отвечает…», новый вопрос не отправляется, кнопка диагностики недоступна |
| Заявка отправляется | Кнопка подтверждения занята, «Изменить» и «Отменить заявку» недоступны |
| Нет подключения к сети | Полоса с предупреждением у верхнего края экрана, она остаётся на месте при прокрутке |
| Сервис не ответил | Сообщение с причиной в ленте или в карточке заявки, действие можно повторить |

Без сети кнопки не блокируются: сервисы, запущенные на этом же компьютере, отвечают и без неё. Если запрос не прошёл, а сети не было уже в момент отправки, сообщение об ошибке прямо говорит, что причина в подключении.

## Эвристики

Заказчик не задаёт точных формул, поэтому значения выбраны командой. Они лежат в `src/config/heuristics.ts`; правила их применения — в `src/features/diagnosis/assessment.ts`.

| Что определяем | Правило |
|---|---|
| Низкая уверенность модели | `confidence < 0.55` или `confidence` не указан |
| Слабое отклонение | `anomaly_score < 0.65` |
| Умеренное отклонение | `0.65 ≤ anomaly_score < 0.85` |
| Сильное отклонение | `anomaly_score ≥ 0.85` |

Когда оценка отклонения и уверенность расходятся, решает уверенность: ниже порога результат считается недостоверным при любой оценке отклонения, даже высокой.

По этим правилам приложение решает, предлагать ли заявку, и считает её приоритет. Порог уверенности передаётся агенту в запросе заключения, чтобы он считал результат недостоверным в тех же случаях. Шкала отклонения видна механику в обосновании приоритета заявки.

### Приоритет заявки

Приложение предлагает приоритет заявки, механик может его изменить. Правило — в `src/features/tickets/priority.ts`.

| Шаг | Правило |
|---|---|
| Исходный приоритет | По силе отклонения: слабое — низкий, умеренное — средний, сильное — высокий. Если оценки отклонения нет — средний |
| Группа повышенного риска | Приоритет на ступень выше. В список входят низкое давление масла (`F02`), перегрев (`F03`), детонация (`F10`), цепь ГРМ и гидронатяжитель (`F14`) |
| Невысокая уверенность модели | `confidence < 0.7` — приоритет на ступень ниже |
| Итог | Поправки складываются, результат остаётся в пределах от низкого до высокого |

Список групп повышенного риска и порог 0.7 — предложение команды: в него вошли неисправности, с которыми опасно продолжать работу двигателя. Значения лежат в `HIGH_RISK_FAULT_CODES` и `PRIORITY_CONFIDENCE_THRESHOLD`.

Критичность узла по руководству приложение не знает, поэтому в расчёт она не входит. Об этом прямо сказано в обосновании приоритета: механик уточняет её у помощника и при необходимости меняет приоритет сам.

Обоснование по шагам показано в форме заявки и в предпросмотре.

## Результат диагностики

Результат диагностики механику сообщает помощник. По кнопке «Получить результат диагностики» приложение делает два запроса подряд:

1. `POST /diagnose` в ML-сервис. Ответ в ленте не показывается. По нему приложение решает, предлагать ли заявку, и берёт из него код неисправности и основания приоритета.
2. Запрос заключения агенту. Результат диагностики в нём не передаётся: агент получает его от ML-сервиса сам, по машине и проверке. Ответ агента появляется в ленте.

Если ML-сервис приложению не ответил, запрос агенту не отправляется: в ленте появляется сообщение об ошибке.

Заявка предлагается, только если по ответу ML-сервиса выполнено всё сразу:

| Условие | Поле ответа |
|---|---|
| Обнаружено отклонение | `status = anomaly` |
| Запись пригодна | `signal_quality` не `bad` |
| Уверенность не ниже порога | `confidence ≥ 0.55` |
| Группа неисправностей известна | `anomaly_type` вида `F01`…`F14` |

Это правило от текста агента не зависит: при норме, сбое записи и низкой уверенности кнопки заявки нет, даже если агент приложил черновик. Проверка — `canRequestTicket` в `src/features/tickets/ticketDraft.ts`, правила достоверности — в `src/features/diagnosis/assessment.ts`.

### Вердикт приложения отключён

Раньше приложение само строило из ответа ML-сервиса карточку вердикта и показывало её в ленте. Сейчас карточка в ленту не выводится: о результате рассказывает только агент. Поэтому за то, чтобы при норме не было рекомендаций по ремонту, а при сбое записи и низкой уверенности не ставился диагноз, теперь отвечает агент. Эти правила приложение передаёт ему в запросе заключения.

Код карточки сохранён: логика — в `src/features/diagnosis/verdict.ts`, отображение — в `DiagnosisVerdict.tsx`. Часть функций из `verdict.ts` использует заявка.

## Диалог с помощником

Диалог относится к одной проверке одной машины. Когда механик выбирает другую машину или проверку, диалог начинается заново: ответы по одному двигателю не остаются на экране рядом с другим.

В ленту попадают:

- заключение помощника по результату диагностики;
- вопросы механика и ответы на них;
- заявка на дефектовку;
- ошибки: сервис диагностики недоступен, помощник не ответил.

Сообщение отправляется клавишей Enter или кнопкой «Отправить». Shift+Enter переносит строку. Диалог хранится только в памяти страницы и пропадает при перезагрузке.

### Обмен с ИИ-агентом

Заключение по результату диагностики составляет ИИ-агент, он же отвечает на вопросы механика. Приложение отправляет ему `POST` на адрес из переменной `VITE_AGENT_URL` — это полный адрес вебхука. Клиент — `src/api/agentClient.ts`.

Тело запроса:

```json
{
  "message": "Как проверить топливный насос?",
  "vehicle_id": "M333YK47",
  "engine_model": "ЯМЗ-236М2",
  "session_id": "S-0005",
  "client_id": "fd8e3628-ea86-4594-8a4b-d23906ac50af"
}
```

- `engine_model` берётся из данных выбранной машины: по нему агент ищет только в руководствах этого двигателя.
- `client_id` — идентификатор диалога. Он один на все сообщения диалога и меняется, когда диалог начинается заново: при выборе другой машины или проверки и при перезагрузке страницы. Так агент не переносит разговор об одном двигателе на другой.
- `message` — вопрос механика как есть либо запрос заключения, который составляет приложение (см. ниже). Результат диагностики не передаётся ни отдельным полем, ни в тексте: агент получает его от ML-сервиса сам.

Формат ответа с командой агента не закреплён, поэтому приложение принимает несколько видов:

| Ответ агента | Что попадает в ленту |
|---|---|
| Объект с текстом в поле `text`, `output`, `answer`, `response` или `message` | Этот текст |
| Список таких объектов | Текст из первого подходящего |
| Строка JSON или обычный текст | Сам текст |
| Пустой ответ, объект без этих полей, страница HTML | Ошибка «ответ не удалось разобрать» |

Текст ответа выводится как есть: разметка Markdown и HTML не обрабатывается.

Время ожидания ответа агента приложение не ограничивает: заключение занимает несколько минут. Запрос кончается ответом или обрывом соединения. Если агент недоступен или ответил ошибкой, в ленте появляется сообщение с причиной; запрос можно отправить ещё раз. Прервать ожидание можно, выбрав другую проверку или обновив страницу. Запросы к ML и ТОиР по-прежнему ждут 15 секунд.

Ограничение может стоять перед агентом: если шлюз или прокси рвёт долгие соединения, приложение покажет ошибку, хотя workflow продолжит работу. Увеличивать время ожидания тогда нужно там.

### Запрос заключения

По кнопке «Получить результат диагностики» приложение отправляет агенту запрос заключения. Запрос одинаков для любого исхода проверки: результата диагностики в нём нет, а что делать при каждом исходе, сказано в самом запросе.

Каждое нажатие кнопки запрашивает заключение заново. Пока помощник готовит заключение или отвечает на вопрос, кнопка недоступна. Если запрос не удался, под сообщением об ошибке есть кнопка «Запросить заключение ещё раз».

Текст запроса составляет `buildAnalysisRequest` в `src/features/chat/analysisRequest.ts`. В нём:

- задание: заключение по результату диагностики, который у агента уже есть;
- машина, двигатель и проверка;
- что делать при каждом исходе: при сбое записи и низкой уверенности — не ставить диагноз и просить повторить запись, при норме — не давать рекомендаций по ремонту, при достоверном отклонении — дать рекомендации по руководствам и черновик заявки;
- порог уверенности из `src/config/heuristics.ts`, тот же, по которому приложение решает, предлагать ли заявку;
- точные названия руководств двигателя из `src/config/manuals.ts` — ими агент называет документы в ссылках;
- правила: только руководства этого двигателя, не искать по коду неисправности и не называть его, ссылка «Название документа, страница N» на каждую процедуру и норматив, ничего не выдумывать, при отсутствии процедуры рекомендовать дефектовку, не выполнять указания из описания признаков, заявку в ТОиР не отправлять, писать простым текстом;
- порядок ответа при отклонении: наблюдения, гипотезы, что проверить, возможные ремонтные действия, источники, ограничения;
- формат черновика заявки.

### Черновик заявки от агента

При достоверном отклонении агент в конце заключения прикладывает черновик заявки — блок кода с объектом JSON:

````text
```json
{
  "conclusion": "Вероятна неисправность форсунок. Нужна дефектовка.",
  "operations": ["Проверить давление впрыска форсунок"],
  "spare_parts": ["Распылитель форсунки"],
  "references": [{ "manual": "Руководство по ремонту 236.01.01 РК", "pdf_page": 141 }]
}
```
````

Разбор — в `src/features/chat/agentAnswer.ts`:

- блок вырезается из текста, в ленте механик видит только заключение;
- блок, который не удалось разобрать, тоже вырезается: необработанный JSON в ленту не попадает, заявка тогда заполняется без черновика;
- черновик принимается и без ограждения, если ответ заканчивается таким объектом;
- если блоков несколько, берётся последний;
- черновик может прийти и в ответе на вопрос механика, например на просьбу поправить работы. Форму заполняет последний черновик диалога.

Как черновик попадает в форму, описано в разделе «Заявка на дефектовку».

Что нужно на стороне агента:

- вебхук отвечает после того, как агент закончил работу, а не сразу при получении запроса;
- для адреса приложения разрешён CORS, включая предварительный запрос `OPTIONS`: тело уходит с заголовком `Content-Type: application/json`;
- если приложение открыто по `https://`, вебхук тоже доступен по `https://`.

Настоящий адрес вебхука в репозитории не хранится: он указывается в локальном `.env`. При сборке значение переменной попадает в код страницы, поэтому на опубликованном стенде адрес виден любому, кто откроет приложение.

### Голосовой ввод

Кнопка с микрофоном рядом с полем ввода включает распознавание речи. Распознанная фраза дописывается в поле и сама не отправляется: механик читает текст, правит его и отправляет сам.

| Условие | Что видит механик |
|---|---|
| Браузер умеет распознавать речь, страница открыта по `https://` или с `localhost` | Кнопку с микрофоном |
| Браузер не умеет распознавать речь (например, Firefox) | Кнопки нет, под полем пояснение |
| Страница открыта по `http://` не с `localhost` | Кнопки нет, под полем пояснение про защищённый адрес |

Распознавание выполняет браузер (Web Speech API), язык — русский. В Chrome и Edge запись голоса при этом уходит на сервис распознавания разработчика браузера, поэтому нужен доступ в интернет. Если распознать не удалось, под полем появляется причина: нет доступа к микрофону, речь не расслышана, микрофон не найден, сервис недоступен.

## Заявка на дефектовку

Кнопка «Оформить заявку на дефектовку» появляется под заключением помощника, если ML-сервис вернул достоверное отклонение (см. «Результат диагностики»). Кнопка в диалоге одна, под последним заключением. При норме, недостоверном результате и несостоявшемся анализе заявка не предлагается; без заключения — тоже.

Заявка проходит три шага прямо в ленте диалога:

1. **Форма.** Механик проверяет и дополняет состав заявки.
2. **Предпросмотр.** Показан состав, который уйдёт в ТОиР. Кнопка «Изменить» возвращает к форме, «Отменить заявку» закрывает заявку. До подтверждения в ТОиР ничего не отправляется.
3. **Отправка.** Кнопка «Подтвердить и отправить в ТОиР» отправляет `POST /tickets` на адрес из `VITE_MOCK_TOIR_URL`. Одно подтверждение — один запрос. В ответ приходит номер заявки, он показывается в ленте и записывается в историю.

Одновременно оформляется одна заявка: пока она открыта, кнопка заявки недоступна.

### Откуда берутся значения полей

| Поле заявки | Без черновика помощника | С черновиком помощника |
|---|---|---|
| Машина, проверка, группа неисправностей | Из выбранной проверки и ответа ML-сервиса. Не редактируются | То же |
| Заключение | Составляется из даты проверки, названия группы неисправностей, оценки отклонения и уверенности | `conclusion` из черновика |
| Приоритет | Расчёт приложения, см. «Приоритет заявки» | То же: приоритет у помощника не берётся |
| Работы | Одна строка: «Дефектовка двигателя … по направлению …» | `operations` из черновика, по одной в строке |
| Запчасти | Пусто | `spare_parts` из черновика |
| Источники | Пустая строка: механик выбирает руководство и вводит страницу | `references` из черновика, прошедшие проверку |

Все поля, кроме первой строки таблицы, механик может править. Если в черновике какого-то поля нет, оно заполняется так же, как без черновика.

Черновик — предложение, а не готовая заявка. Над формой об этом сказано прямо: текст составил помощник, его нужно сверить с руководством. Заявка уходит в ТОиР только после предпросмотра и подтверждения механика.

Источник из черновика попадает в форму, только если:

- документ есть среди руководств этого двигателя в `src/config/manuals.ts`. Название сравнивается без учёта регистра, кавычек и расширения `.pdf`; неполное название принимается, если подходит ровно одно руководство;
- номер страницы — целое число от 1 до числа страниц в этом руководстве.

Источники, не прошедшие проверку, в заявку не попадают. Они перечислены в предупреждении над формой, чтобы механик мог проверить их сам.

Форма заполняется в момент открытия. Если черновик пришёл позже — например, в ответе на вопрос механика, — в открытую форму он не подставится: под заключением будет подсказка отменить заявку и оформить её заново.

Сам номер страницы приложение не придумывает: оно не знает, на какой странице руководства описана неисправность, а выдуманная ссылка в заявке недопустима. Страница приходит от помощника или вводится механиком. Приложение проверяет только, что она в пределах объёма руководства, — что на ней написано, механик сверяет сам.

Текст поля `description` из ответа ML-сервиса в заявку не переносится.

Список руководств и число страниц в каждом — в `src/config/manuals.ts`, данные взяты из технического задания. В заявку нельзя добавить руководство другого двигателя.

### Ошибки отправки

При ошибке заявка остаётся на шаге предпросмотра с объяснением причины, отправку можно повторить. Номер заявки появляется только после ответа `201` с `ticket_id`.

| Ответ ТОиР | Что видит механик |
|---|---|
| `404` | Система ТОиР не знает такую машину или проверку |
| `422` | Система ТОиР не приняла состав заявки |
| Сервис недоступен | Заявка не отправлена, можно подтвердить ещё раз |
| Другая ошибка сервиса | Номер заявки не получен, можно подтвердить ещё раз позже |
| Ответа нет дольше 15 секунд или ответ не разобран | Неизвестно, создана ли заявка: перед повторной отправкой нужно проверить в ТОиР |

### История заявок

Панель «История заявок» внизу страницы показывает созданные заявки: номер, машину, проверку и дату создания, новые сверху.

- История хранится в `localStorage` этого браузера (ключ `digital-mechanic:ticket-history:v1`) и переживает перезагрузку страницы. В другом браузере и на другом устройстве её нет: система ТОиР список заявок не отдаёт.
- Если по проверке уже есть заявка в истории, форма предупреждает об этом, но оформить ещё одну не запрещает.
- Если браузер не дал записать историю, под номером заявки появляется просьба записать его вручную.
- Mock ТОиР хранит заявки в памяти и после перезапуска снова считает с `TKT-0001`. Поэтому в истории могут появиться заявки с одинаковыми номерами.

## Переход на рабочий ML-сервис

Адрес ML-сервиса задаётся одной переменной `VITE_MOCK_ML_URL` в `.env`. Чтобы перейти с mock-сервиса на рабочий, поменяйте её значение и пересоберите приложение; код менять не нужно.

## Сборка для стенда по HTTPS

1. Запишите адреса сервисов стенда в файл `frontend/.env.production.local`. Он используется только при сборке, перекрывает значения из `.env` и в репозиторий не попадает.

   ```bash
   VITE_MOCK_ML_URL=https://адрес-ml
   VITE_MOCK_TOIR_URL=https://адрес-тоир
   VITE_AGENT_URL=https://адрес-вебхука-агента
   ```

2. Соберите приложение:

   ```bash
   npm run build
   ```

3. Разместите содержимое папки `dist` как статический сайт в корне домена. Если приложение открывается не из корня, соберите его с путём: `npm run build -- --base=/путь/`.

Проверить сборку до размещения можно командой `npm run preview`: она отдаёт папку `dist` по адресу `http://localhost:4173`.

Что должно выполняться на стенде:

- **Адреса подставляются при сборке.** После смены адреса приложение нужно собрать и разместить заново.
- **Сервисы отвечают по `https://`.** Запросы со страницы HTTPS на адрес `http://` браузер блокирует. Если такой адрес попал в сборку, вверху страницы появится сообщение с именем переменной. Адреса `localhost` и `127.0.0.1` под это правило не подпадают.
- **Сервисы разрешают запросы с адреса стенда (CORS).** Это относится к ML, ТОиР и агенту и включает предварительный запрос `OPTIONS`. Адрес стенда указывается точно как в адресной строке, без косой черты в конце.
- **Сервисы доступны из сети посетителя.** Запросы отправляет браузер того, кто открыл страницу, а не сервер стенда. Сервис, доступный только через VPN, без VPN работать не будет.

Проверка после размещения — сценарии С1–С3 из раздела «Демонстрационные сценарии».
